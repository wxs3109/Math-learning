## 9.1 Prompt 在数学上做了什么 **[事实 + 直觉]**

模型的参数 $\theta$ 在推理时是固定的。我们能控制的只有输入序列 $c$（context），输出服从
$$y\sim p_\theta(y\mid c)=\prod_t p_\theta(y_t\mid c,y_{<t}).$$
所以**prompt engineering 就是选择条件 $c$**，让我们想要的输出在这个条件分布下概率最高。

**为什么措辞会影响结果**：预训练让模型学会了"什么样的前文后面通常跟什么样的后文"。
- 一段像教科书的前文，后面更可能跟严谨的推导；
- 一段像论坛帖子的前文，后面更可能跟随意的回答。

instruction tuning（[8.4 节](ch08-pre-post-training.md#8.4)）之后，模型学会了"按指令做事"这种格式，但这一点没有变：前文决定了后文的分布。

**in-context learning 的一种解释** **[直觉]**：可以把预训练语料想成很多种"任务"的混合。提示里的例子是证据，模型隐式地做了贝叶斯推断：
$$p(\text{任务}\mid\text{例子})\propto p(\text{例子}\mid\text{任务})\,p(\text{任务}),$$
然后按推断出的任务来回答。这个模型很简化，但能解释几个现象（9.9.3 节）：
- 一个例子往往有歧义，多个**不同**的例子才能把任务确定下来；
- 例子的格式会被模仿，因为它也是证据的一部分。

## 9.2 消息、角色和 chat template **[事实]**

API 里的对话是一个消息列表，每条消息有角色：
- **system**：长期有效的设定，比如身份、规则、输出格式；
- **user**：用户输入；
- **assistant**：模型之前的回答。

**模型并不真的"知道"角色**。推理前，消息列表按**chat template**拼成一条序列，角色只是其中的特殊标记，最后以"assistant 开始说话"的标记结尾，模型从那里接着往下写（9.9.1 节）。不同模型家族的特殊标记不同，所以开源模型一定要用它自带的模板。

**几个推论**：
- system 提示之所以"更有权威"，是因为 instruction tuning 时模型被训练得更重视它，不是因为结构上有什么特殊。
- 多轮对话每一轮都要把完整历史重新发一遍。模型本身没有记忆，"记忆"就是上下文（第 11 章）。
- 历史越长，每次调用越贵、越慢（[6.4 节](ch06-self-attention.md#6.4)）。

## 9.3 写清楚 **[经验]**

**金标准**：把提示给一位对任务一无所知的同事看。如果他会困惑，模型也会。把模型当成一个聪明但刚入职、不了解你们背景的新员工。

**一份好提示通常包括**：
1. **任务**：用动词开头，说清楚要做什么。
2. **背景**：为什么要做，给谁看，用在哪里。背景能帮模型在指令没覆盖到的地方做出合理选择。
3. **约束**：长度、语气、不能做什么。
4. **输出格式**：给出具体的格式，最好附一个例子。

**用 XML 标签分隔不同部分**：
```
<instructions>把下面的合同条款翻译成英文，保留条款编号。</instructions>
<contract>
……合同原文……
</contract>
<format>每条一行：编号 + 译文</format>
```
标签让模型分清"哪些是指令、哪些是材料"。在提示里也用标签名指代内容，比如"按 `<format>` 的格式输出"。

**说要做什么，而不是不要做什么**："用连贯的段落写"比"不要用列表"更有效。

**给出原因**："不要用省略号，因为这段文字会被语音合成朗读"比单纯的"不要用省略号"效果好，模型能把原因推广到类似情况。

## 9.4 Few-shot 例子 **[经验 + 直觉]**

例子是控制输出格式和风格最可靠的手段之一。
- **3–5 个**通常足够。
- **要多样**：覆盖不同情况，否则模型会抓住例子之间偶然的共同点（比如都很短）。
- **要准确**：错误的例子也会被模仿。
- 用 `<example>` 标签包起来，和真正的输入分开。

**zero-shot、few-shot、微调怎么选**：
- 先试 zero-shot，把指令写清楚；
- 格式或风格对不上，加例子；
- 例子多到塞不下、或者需要大量领域知识时，再考虑检索（第 15 章）或微调。

## 9.5 让模型先想 **[事实 + 直觉]**

**chain-of-thought**（CoT）：让模型先写出推理过程，再给答案。现在的模型大多有内置的"思考"模式（extended thinking），由 API 参数控制思考的预算。

**为什么有用** **[直觉]**：
- 语言模型每生成一个 token，做的计算量大致固定。复杂的问题需要更多计算，写出中间步骤等于给了它更多"计算步数"。
- 中间结果写在上下文里，后面的 token 可以通过注意力读到它们（[第 6 章](ch06-self-attention.md)），相当于草稿纸。

**实践中**：
- 复杂推理、多步计算、需要权衡的决定，打开思考或者要求先分析再回答；
- 简单的分类、抽取，不需要思考，打开只会增加延迟和费用；
- 需要解析输出时，让推理和答案分开，比如分别放在 `<thinking>` 和 `<answer>` 里。

## 9.6 解码参数 **[已证 + 事实]**

模型每一步输出 logits $z\in\mathbb R^V$，再转成概率并采样。常用的三个参数：

**温度** $T$：
$$p_i(T)=\frac{e^{z_i/T}}{\sum_je^{z_j/T}}.$$
- $T\to0$：趋于贪心解码（总选概率最大的 token）；
- $T=1$：模型原始的分布；
- $T>1$：分布更平，更"有创意"也更容易出错。

用熵（[1.7 节](ch01-probability.md#1.7)）衡量，$T$ 越大熵越大。$2^{H}$ 可以理解为"有效候选数"（9.9.2 节）。

**top-k**：只保留概率最大的 $k$ 个 token，重新归一化。

**top-p**（nucleus）：按概率从大到小累加，只保留累计概率刚超过 $p$ 的最小集合。它能自适应：分布尖的时候只剩几个候选，分布平的时候保留很多。它的主要作用是**砍掉长尾**：长尾里每个 token 概率都很小，但加起来不小，偶尔抽中就会产生离谱的输出。

**实践中** **[经验]**：
- 抽取、分类、代码：低温度；
- 创意写作、头脑风暴：温度高一些；
- 一般只调温度或 top-p 中的一个；
- 温度设为 0 也不保证每次输出完全一样：服务端的 batching 和浮点运算顺序都可能带来细小差别。需要可复现时，把输出存下来。

## 9.7 Structured output 与 constrained decoding **[事实]**

**问题**：下游程序要解析模型输出，比如 JSON。只靠提示，模型偶尔会输出不合法的格式：少一个括号、多一句解释、类型不对。

**constrained decoding**：
- 把 JSON Schema 编译成一个语法（或状态机）；
- 每一步只允许语法上合法的 token，把其余 token 的 logit 设为 $-\infty$；
- softmax 之后这些 token 的概率恰好为 0，所以输出**一定**合法（9.9.4 节）。

各家 API 都提供了这个功能，通常叫 structured outputs 或 strict 模式；tool calling 的参数也可以这样约束（第 10 章）。

**注意**：
- 约束保证的是**格式**，不保证**内容**正确。字段值依然可能是错的。
- 约束太紧可能让模型"无路可走"，只好输出语法合法但语义很差的内容。让 schema 留出表达"不知道"的余地，比如允许 `null`。

## 9.8 从 prompt engineering 到 context engineering **[事实 + 直觉]**

单轮问答时，要优化的主要是一条提示。Agent 要跑很多轮（第 11 章），上下文里会累积 system prompt、工具定义、对话历史、文件内容、工具返回结果。这时要管理的是**整个上下文**，这叫**context engineering**。

**为什么上下文是稀缺资源**：
- **成本**：每次调用都要处理全部上下文，费用和延迟随长度增长。
- **注意力被摊薄**：注意力要在所有位置之间分配（[第 6 章](ch06-self-attention.md)），无关内容越多，关键信息越容易被忽略。实验中观察到，上下文越长，模型从中准确找回信息的能力越弱，这被称为 context rot。

**由此得到的原则** **[经验]**：
- 放进上下文的每一段都应该有用。要找的是"让期望结果最可能出现的最小一组高信息量 token"。
- 长文档放在前面，问题放在最后。
- 需要时再取（检索、读文件），而不是一开始全塞进去（第 11、13、15 章）。

## 9.9 数值实验

代码：[`code/ch09_prompting.py`](code/ch09_prompting.py)，只依赖 numpy，`python3 ch09_prompting.py` 直接运行。代码不调用真实模型，而是把 prompt engineering 背后的几件"机械"事实单独拿出来验证。

### 9.9.1 Chat template

四条消息（system、user、assistant、user）被拼成一条字符串，每条消息用 `<|im_start|>角色` 和 `<|im_end|>` 包起来，最后以 `<|im_start|>assistant` 结尾。模型看到的就是这一条序列，它要做的只是从末尾接着写。

### 9.9.2 解码参数

一个 10 个候选的 logits 向量，不同温度下：

| 温度 $T$ | 最大概率 | 熵（bit） | 有效候选数 $2^H$ |
|---|---|---|---|
| 0.2 | 0.864 | 0.66 | 1.6 |
| 0.5 | 0.544 | 1.85 | 3.6 |
| 1.0 | 0.330 | 2.65 | 6.3 |
| 1.5 | 0.249 | 2.95 | 7.7 |
| 3.0 | 0.170 | 3.20 | 9.2 |

- top-k=3 只留下 3 个候选；top-p=0.9 留下 6 个，"猫""量子""香蕉"这些长尾被砍掉。
- $T=1$ 时，"香蕉"的概率是 0.0037，10 万次采样中出现了 0.38%。概率小不等于不会发生，top-p 之后它的概率变成 0。

### 9.9.3 Few-shot = 贝叶斯更新

假设有 5 种任务（大写、反转、首字母、长度、原样），先验均匀，例子有 5% 的噪声。逐个加入例子 `a→a`、`cat→CAT`、`dog→DOG`、`moon→MOON`，"任务"的后验：

| 例子数 | 大写 | 反转 | 首字母 | 长度 | 原样 |
|---|---|---|---|---|---|
| 0 | 0.200 | 0.200 | 0.200 | 0.200 | 0.200 |
| 1 | 0.017 | 0.322 | 0.322 | 0.017 | 0.322 |
| 2 | 0.247 | 0.247 | 0.247 | 0.013 | 0.247 |
| 3 | **0.862** | 0.045 | 0.045 | 0.002 | 0.045 |
| 4 | **0.992** | 0.003 | 0.003 | 0.000 | 0.003 |

- 第一个例子 `a→a` 没有代表性：它同时符合"反转""首字母""原样"，反而把真正的任务"大写"压低了。
- 再加入几个**不同**的例子，后验才集中到"大写"上。这就是 9.4 节"例子要多样、要有代表性"的原因。

### 9.9.4 Constrained decoding

一个"随机模型"每步给出任意 logits，要生成形如 `{"age": 42}` 的输出：
- 不加约束：2000 次生成里合法的比例是 **0.000**；
- 用状态机屏蔽非法字符：合法的比例是 **1.000**，例如 `{"age": 081}`。

这个例子也说明了"约束只管格式"：`081` 格式合法，但通常不是我们想要的写法。

## 9.10 小结与疑问

**搞懂了什么**：
- 提示就是条件分布里的条件；角色只是 chat template 里的特殊标记。
- 写清楚任务、背景、约束和格式；用 XML 标签分隔；给 3–5 个多样的例子；复杂问题让模型先想。
- 温度控制分布的平坦程度，top-p 砍掉长尾；constrained decoding 保证格式，不保证内容。
- 上下文是稀缺资源，Agent 时代要管理的是整个上下文。

**疑问**：
- "in-context learning 是隐式贝叶斯推断"这个解释，在多大程度上符合真实模型的内部机制？
- 怎样系统地比较两版提示的好坏？靠感觉不行，要靠评测（第 16 章）。
