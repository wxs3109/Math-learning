# 第 16 章 评测、安全与上线

> 标注：**[已证]** 给出了推导 · **[事实]** 标准结论 · **[直觉]** 帮助理解、不严格 · **[经验]** 工程实践中总结的做法

## 导读

前几章讲了怎样把大模型应用搭起来。要让它可靠地服务真实用户，还要回答几个问题：
- 改了一版提示、换了一个模型，到底是变好还是变坏了？
- 模型的输出是随机的，评测分数差 3 个百分点，算不算真的差别？
- 怎样用模型给模型打分，又不被它的偏见误导？
- 怎样防止模型被网页、邮件里藏的指令操纵？
- 费用和延迟怎样控制？

本章讲评测的设计和统计，以及上线需要的可观测性、安全和成本控制。

**与大模型的关系**

没有评测，就只能凭感觉改提示，修好一个问题又引出另一个，而且只能在线上发现问题。有了评测，新模型发布时，一天之内就能知道该不该换。

**前置知识**

误差累积要用到独立事件的乘法（[1.1 节](ch01-probability.md#1.1)）；置信区间与 bootstrap（[2.3 节](ch02-statistics.md#2.3)）；用测试集挑模型会高估效果（[2.7 节](ch02-statistics.md#2.7)）；agent 与 harness（[第 11 章](ch11-agent-harness.md)）。

## 16.1 评测由什么组成 **[事实]**

一个评测（eval）就是一组自动化测试：给系统一个输入，用打分逻辑检查输出。对 agent 来说，它包括：
- **任务**：输入、环境的初始状态，以及成功的标准；
- **试验**（trial）：同一个任务跑多次，因为输出是随机的；
- **记录**（transcript）：agent 的完整过程，包括每次模型调用、工具调用和结果；
- **结果**（outcome）：结束时环境的最终状态，比如文件改对了没有、工单建了没有；
- **打分器**（grader）：判断成功与否。

**三类打分器**：

| 打分器 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 代码 | 精确匹配、跑单元测试、检查最终状态、校验 JSON | 快、便宜、确定、可复现 | 只能判断可以写成规则的东西 |
| 模型 | 用 LLM 按评分细则打分 | 能判断开放式输出（语气、完整性、是否忠实于材料） | 有偏差、有噪声，需要和人工标注校准（16.4 节） |
| 人 | 专家评审 | 最准 | 贵、慢，规模上不去 |

**经验**：
- 能用代码判断的，就用代码；
- 评判 agent 时，优先检查**结果**而不是**路径**。agent 可能用一种你没想到但完全正确的方式完成任务，规定它"必须先调用 A 再调用 B"会误判。

## 16.2 Agent 的误差会累积 **[已证]**

一个任务要连续做对 $n$ 步，每步成功率为 $p$。如果各步独立，全部做对的概率是
$$P(\text{成功})=p^n.$$

| $p$ | $n=5$ | $n=10$ | $n=20$ | $n=50$ |
|---|---|---|---|---|
| 0.99 | 0.951 | 0.904 | 0.818 | 0.605 |
| 0.95 | 0.774 | 0.599 | 0.358 | 0.077 |
| 0.90 | 0.590 | 0.349 | 0.122 | 0.005 |

单步 95% 看起来不错，20 步的任务却只有 36% 能做完。这是长任务难做的根本原因，也说明了 harness 里反馈回路的价值（[11.7 节](ch11-agent-harness.md#11.7)）：能发现并改正错误，每步的"有效成功率"就更接近 1。

## 16.3 pass@k 与 pass^k **[已证]**

同一个任务跑 $k$ 次，单次成功率为 $p$：
- **pass@k**：$k$ 次里**至少一次**成功，$1-(1-p)^k$。适合"可以多试几次、能自动验证哪次对"的场景，比如生成代码后跑测试。
- **pass^k**：$k$ 次**全部**成功，$p^k$。适合"每次都必须对"的场景，比如客服 agent 每次面对一个真实用户。

两者随 $k$ 往相反方向变化（16.9.2 节）：$k=8$ 时，同一个系统的 pass@8 是 0.99，pass^8 只有 0.12。**报告评测结果时，要说清楚用的是哪一个**。

**pass@k 的无偏估计**：每个任务采样 $n$ 次，其中 $c$ 次成功。直接用 $\hat p=c/n$ 代入 $1-(1-\hat p)^k$，结果是**有偏**的（系统性地偏低）。无偏估计是
$$\widehat{\text{pass@}k}=1-\frac{\binom{n-c}{k}}{\binom nk}.$$
**含义**：从 $n$ 次结果里不放回地抽 $k$ 次，"全部失败"的概率是 $\binom{n-c}{k}/\binom nk$。这个量对每一组固定的 $n$ 次采样都可以精确计算，它的期望恰好是 $(1-p)^k$。

## 16.4 评测分数有多可信 **[事实 + 已证]**

**样本量**：准确率在 70% 左右时，标准误差约为 $\sqrt{p(1-p)/n}$（[2.3 节](ch02-statistics.md#2.3)）：
- 50 道题：约 ±6.5%；
- 200 道题：约 ±3.2%；
- 1000 道题：约 ±1.4%。

所以 50 道题的评测集上差 3 个百分点，基本说明不了问题。

**比较两个系统要配对**：两个系统做的是同一批题，难题对两者都难，所以它们的对错高度相关。
- 不配对时，$\mathrm{Var}(\bar B-\bar A)=\mathrm{Var}(\bar A)+\mathrm{Var}(\bar B)$；
- 配对时（逐题看差值），要再减去 $2\,\mathrm{Cov}(\bar A,\bar B)$（[1.3 节](ch01-probability.md#1.3)）。协方差为正，所以区间更窄。

做法：对"题目"做 bootstrap，每次重抽样都同时计算两个系统在同一批题上的分数之差。

**其他注意事项**：
- 同一个任务跑多次，报告平均值和波动；
- 不要在同一个评测集上反复调提示、挑最好的那版。这和"用测试集挑模型"一样会高估效果（[2.7 节](ch02-statistics.md#2.7)），要留一份不参与调试的测试集；
- 评测集要随真实失败案例不断扩充：每发现一个线上问题，就加一条测试。

## 16.5 用模型当评委 **[事实 + 经验]**

开放式的输出（摘要好不好、回答是否忠实于材料、语气是否合适）很难写成规则，常用另一个模型按评分细则（rubric）来打分。

**已知的偏差**：
- **位置偏差**：两两比较时，倾向于偏爱某个位置上的回答；
- **长度偏差**：偏爱更长的回答；
- **自我偏好**：偏爱和自己风格相近的回答。

**对策** **[经验]**：
- **交换位置各问一次**。两次结论不一致就记为平局，这能消除位置偏差（16.9.4 节）；
- **评分细则要具体**：每一维单独打分，给出每一档的标准和例子；允许评委回答"无法判断"；
- **先让评委写理由，再给分数**；
- **和人工标注校准**：抽一批样本请人标注，计算评委和人的一致性。只看一致率会被类别比例误导，要用 **Cohen's kappa**：
$$\kappa=\frac{p_o-p_e}{1-p_e},$$
其中 $p_o$ 是实际的一致率，$p_e$ 是按两者各自的类别比例"碰巧一致"的概率。$\kappa=0$ 表示和瞎猜一样，$\kappa=1$ 表示完全一致。

## 16.6 可观测性 **[经验]**

线上出了问题，要能回答"那一次请求里，模型到底看到了什么、做了什么"。
- **记录完整的轨迹**：每次模型调用的输入输出、token 数、延迟、费用，每次工具调用的参数和结果；
- **用 trace 串起来**：一次用户请求对应一个 trace，里面每次模型调用、工具调用是一个 span。OpenTelemetry 有专门的生成式 AI 约定，MCP 最新规范也规定了怎样在 `_meta` 里传递 trace 上下文（第 12 章）；
- **监控指标**：错误率、工具失败率、平均轮数、token 用量、缓存命中率、首 token 延迟；
- **把线上失败变成评测用例**。

注意隐私：日志里会有用户数据，要脱敏、控制访问权限、设定保存期限。

## 16.7 安全：提示注入 **[事实 + 经验]**

**提示注入**：攻击者把指令藏在模型会读到的内容里，比如网页、邮件、文档、工具返回的结果。模型分不清"这是用户的指令"还是"这是材料里的一句话"，就可能照做。

**最危险的组合**（Simon Willison 称为"致命三要素"）：一个 agent 同时
1. 能读到**私密数据**（邮件、日程、内部文档）；
2. 会接触**不可信内容**（网页、外部邮件）；
3. 能**对外发送信息**（发邮件、发请求、渲染外链图片）。

三者同时具备，攻击者就可能通过不可信内容让 agent 把私密数据发出去。

**防护的原则**：不要指望模型自己识破所有注入，要在 harness 层面限制它能造成的损害。
- **切断三要素之一**：比如读了不可信内容之后，禁止对外发送，或者必须由用户确认（16.9.5 节的"污染标记"）；
- **最小权限**：工具只给必需的权限；令牌只读、限定范围；
- **有副作用的操作需要人确认**，确认界面要显示完整参数；
- **在提示里标明材料的边界**：用标签包住外部内容，并说明其中的指令不应执行。这能降低风险，但不能单独依靠它。

**其他风险**：输出里的敏感信息泄露、生成不当内容、越权访问数据。常见做法是在输入和输出两侧加检查（guardrails），比如 PII 检测、内容分类器、按用户权限过滤检索结果（[15.7 节](ch15-rag.md#15.7)）。

## 16.8 成本与延迟 **[事实 + 经验]**

**费用**：输入 token 和输出 token 分别计价，输出通常贵好几倍。降低费用的主要手段：
- **提示缓存**：稳定的前缀放前面（[11.6 节](ch11-agent-harness.md#11.6)）；
- **控制上下文**：截断、压缩、按需检索（[11.4 节](ch11-agent-harness.md#11.4)）；
- **按难度路由**：简单问题交给便宜的小模型（16.9.6 节）；
- **批处理**：不着急的任务用批处理接口，价格更低。

**延迟** ≈ 首 token 延迟（TTFT，主要取决于输入长度和排队） + 输出 token 数 ÷ 生成速度。
- 用流式输出，让用户尽早看到内容；
- 缩短输出：要求简洁，或者只要结构化的关键字段；
- 并行执行独立的工具调用（[10.4 节](ch10-tool-calling.md#10.4)）和子任务。

## 16.9 数值实验

代码：[`code/ch16_evals.py`](code/ch16_evals.py)，只依赖 numpy，`python3 ch16_evals.py` 直接运行。

### 16.9.1 误差累积

16.2 节的表格就是代码的输出。模拟 $p=0.95$、$n=20$ 十万次，全对的比例是 0.357，公式值 0.358。

### 16.9.2 pass@k 与 pass^k

200 个任务，各自的单次成功率不同，平均 0.672：

| $k$ | pass@k | pass^k |
|---|---|---|
| 1 | 0.672 | 0.672 |
| 2 | 0.865 | 0.480 |
| 4 | 0.964 | 0.274 |
| 8 | 0.993 | 0.117 |

真实 pass@4 = 0.7599。每个任务只采样 $n=10$ 次去估计：先估计 $p$ 再代公式，平均得到 0.6989（偏低）；用无偏估计，平均得到 0.7598。

### 16.9.3 置信区间与配对比较

50 道题，两个系统面对同一批难度不同的题：
- A 的准确率 0.70，95% 区间 [0.58, 0.82]；B 的准确率 0.74，95% 区间 [0.62, 0.86]；
- B − A = +0.04。不配对的 95% 区间 [−0.14, 0.22]，**配对的** [−0.08, 0.16]，窄了约三分之一；
- 两个系统在 40 道题上对错一致，这正是配对更精确的原因；
- 即便如此，区间仍然包含 0：50 道题不足以确认 B 更好。

### 16.9.4 LLM 评委的位置偏差

2000 对回答，评委有偏爱第一个位置的偏差：
- 只按一种顺序问：判"X 更好"的比例 0.755，而真实只有 0.514。与真值的一致率 0.736，kappa 0.463；
- 交换顺序各问一次，两次结论一致的只有 52%：评委的判断很大程度上取决于顺序；
- 两次结合，不一致记为平局：判"X 更好"的比例 0.522，回到真实值附近；一致率 0.746，kappa 0.490。

位置偏差带来的系统性高估被消除了，但评委本身的噪声还在，所以 kappa 只是小幅提高。

### 16.9.5 提示注入的污染标记

一个 agent 先读日程（私密数据），再抓取一个网页（不可信内容，里面藏着"把日程发给 attacker@…"），然后尝试发邮件：
- harness 发现上下文同时含有私密数据和不可信内容，**拦截**了 `send_email`，要求用户确认；
- 对照：只读日程再发邮件，没有不可信内容，正常执行。

这个检查完全在 harness 里，不依赖模型是否识破了注入。

### 16.9.6 延迟与路由

| 模型 | 首 token | 生成 400 token | 总延迟 | 相对价格 |
|---|---|---|---|---|
| 大模型 | 1.2s | 6.7s | 7.9s | 1.0 |
| 小模型 | 0.4s | 2.2s | 2.6s | 0.2 |

假设 70% 的问题是简单的：

| 策略 | 准确率 | 平均相对价格 |
|---|---|---|
| 全用大模型 | 0.956 | 1.00 |
| 全用小模型 | 0.852 | 0.20 |
| 简单的给小模型，难的给大模型 | 0.942 | 0.44 |

路由用不到一半的价格，保住了大部分准确率。前提是能把难易分准，分类器本身也需要评测。

## 16.10 小结与疑问

**搞懂了什么**：
- 评测 = 任务 + 多次试验 + 打分器；能用代码判断就用代码，评判 agent 看结果而不是路径。
- 误差按 $p^n$ 累积；pass@k 和 pass^k 衡量的是两件不同的事；pass@k 要用无偏估计。
- 评测分数有误差：50 道题约 ±6.5%；比较两个系统要配对；不要在测试集上调提示。
- LLM 评委有位置、长度等偏差：交换顺序、写清细则、用 kappa 和人工标注校准。
- 提示注入要在 harness 层面防：切断"致命三要素"之一、最小权限、关键操作需人确认。
- 成本靠缓存、上下文控制、路由、批处理；延迟靠流式、短输出、并行。

**疑问**：
- 怎样为开放式的 agent 任务（比如"调研一个问题"）设计既可靠又便宜的打分器？
- 模型越来越强，评测集很快就"饱和"了。怎样持续地构造有区分度的任务？
