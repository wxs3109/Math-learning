# 第 11 章 Agent 与 harness

> 标注：**[已证]** 给出了推导 · **[事实]** 标准结论 · **[直觉]** 帮助理解、不严格 · **[经验]** 工程实践中总结的做法

## 导读

第 10 章讲了一次工具调用。把它放进一个循环，让模型自己决定下一步调用什么、什么时候停，就得到了 **agent**。真正让 agent 能干活的，除了模型，还有包在模型外面的那层程序，叫 **harness**。本章讲：
- 什么时候用固定流程（workflow），什么时候用 agent；
- agent 循环；
- harness 由哪些部件组成：工具、上下文管理、权限、钩子、恢复；
- 上下文管理：截断、压缩、笔记、子 agent；
- 提示缓存与成本。

**与大模型的关系**

一个常见的说法是 **Agent = Model + Harness**。模型决定"想做什么"，harness 决定"模型能看到什么、能做什么、做错了怎么办"。同一个模型放进不同的 harness，表现可以差很多。编程助手（如 Claude Code）、深度研究、客服机器人，本质上都是"模型 + 一个专门设计的 harness"。

## 11.1 Workflow 还是 agent **[事实 + 经验]**

Anthropic 在 *Building effective agents* 里把"agentic 系统"分成两类：
- **Workflow**：模型和工具按**预先写好的代码路径**编排；
- **Agent**：模型**自己决定**流程和工具的使用，直到完成任务。

**五种常见的 workflow 模式**：

| 模式 | 做法 | 例子 |
|---|---|---|
| 提示链 | 把任务拆成固定的几步，每步处理上一步的输出，中间可以加程序检查 | 先写大纲、检查大纲、再写全文 |
| 路由 | 先分类，再交给专门的提示或模型 | 简单问题给小模型，难题给大模型 |
| 并行 | 同时跑多个调用，再汇总；或者同一问题问多次再投票 | 多个评审维度并行打分 |
| 编排者–工作者 | 一个模型拆分子任务，分给多个工作者，再汇总 | 一次要改很多文件的代码修改 |
| 评估者–优化者 | 一个模型生成，另一个评估并给反馈，循环到满意为止 | 翻译反复润色 |

**原则** **[经验]**：**先找最简单的方案，确实需要时才加复杂度**。
- 一次调用加上好的提示和检索就能解决的，不要做 agent；
- 步骤固定、可预测的任务，用 workflow；
- 步骤数量和路径事先无法确定的任务（改一个陌生代码库里的 bug、开放式调研），才需要 agent。

Agent 更灵活，但代价是延迟、费用更高，错误会累积（第 16 章会算这个账）。

## 11.2 Agent 循环 **[事实]**

一句话定义：**agent 就是在循环里调用工具来完成目标的语言模型**。
```
messages = [用户的任务]
loop:
    reply = model(system, tools, messages)
    messages.append(reply)
    if reply 里没有工具调用: break          # 模型认为完成了
    results = [执行(c) for c in reply 的工具调用]   # 过权限检查、钩子
    messages.append(results)
```

**停止条件**：
- 模型不再调用工具（正常结束）；
- 达到轮数、时间或费用上限（防止死循环）；
- 用户中断。

**两个关键点**：
- 循环本身很简单，几行代码就能写完（11.8.1 节）。难的是循环外面的一切，也就是 harness。
- 每一轮，模型都要重新读一遍越来越长的上下文。成本和上下文管理的问题由此而来（11.4、11.6 节）。

## 11.3 Harness：模型之外的一切 **[事实 + 直觉]**

Harness 可以分成四块：

**1. 循环与执行**：调用模型、解析回复、执行工具、处理错误、重试、超时、中断后恢复。

**2. 工具接口**：给模型哪些工具，怎样描述，结果怎样格式化（[10.3 节](ch10-tool-calling.md#10.3)）。编程 agent 的典型工具是：读文件、改文件、搜索、执行命令。

**3. 上下文管理**：每一轮让模型看到什么（11.4 节）。包括：
- 系统提示和项目说明文件（如 `CLAUDE.md`、`AGENTS.md`）；
- 工具定义；
- 按需加载的知识，比如 Skills（第 13 章）；
- 对话历史和工具结果，以及对它们的截断、压缩。

**4. 控制**：权限、沙箱、人工确认、钩子、审计日志（11.5 节）。

**为什么 harness 这么重要** **[直觉]**：模型只能看到 harness 给它的东西，只能做 harness 允许的事。很多 agent 失败，原因不是模型不够聪明，而是：
- 上下文里没有它需要的信息；
- 或者塞满了无关的信息；
- 工具不好用，或者错误信息不清楚；
- 没有反馈，比如不跑测试就不知道改对了没有。

## 11.4 上下文管理 **[事实 + 经验]**

长任务里，上下文会不断变长：每读一个文件、每执行一条命令，结果都留在历史里。上下文太长会带来三个问题：超过窗口上限、费用和延迟上升、注意力被摊薄（[9.8 节](ch09-prompt-engineering.md#9.8)）。常用手段：

**截断工具结果**：
- 读文件默认只读前若干行，告诉模型还剩多少、怎样读后面的部分；
- 命令输出只保留头尾。

**即时检索**（just-in-time）：上下文里放文件路径、查询语句这些"指针"，需要时再用工具去读，而不是一开始把所有文件读进来。

**压缩**（compaction）：上下文接近上限时，让模型把到目前为止的工作总结成一段摘要（目标、已完成的事、关键发现、下一步），用摘要替换旧的历史，然后接着干。
- 好处：可以无限期地跑下去。
- 风险：摘要会丢细节。所以摘要的提示要写清楚保留什么（未解决的问题、关键决定、文件路径）。
- 现在主流的 API 和框架都内置了压缩：设一个 token 阈值，超过就自动总结。

**结构化笔记**：让 agent 把进度写进上下文之外的文件，比如待办清单或进度文档，之后需要时再读回来。压缩丢掉的细节，可以从笔记里找回。

**子 agent**：把一个需要大量探索的子任务交给另一个拥有**独立上下文**的 agent。它可能读了几十个文件，但只把一段精炼的结论返回给主 agent。主 agent 的上下文因此保持干净。代价是总 token 更多，而且子 agent 之间不共享细节。

## 11.5 权限、沙箱与人在回路 **[事实 + 经验]**

模型会犯错，也可能被工具结果里的恶意内容误导（提示注入，第 16 章）。执行权在 harness 手里，所以安全措施也放在 harness 里。

**权限分级**：
- 只读操作（读文件、搜索）：直接放行；
- 有副作用的操作（写文件、执行命令、发消息）：按规则放行，或者请求用户确认；
- 不可逆的操作（删除、付款、对外发布）：默认拒绝或必须确认。

**被拒绝也要返回结果**：把"权限拒绝"作为 `tool_result` 返回（11.8.1 节）。模型看到后会调整计划，而不是卡住或反复重试。

**沙箱**：在隔离的环境（容器、受限的文件系统和网络）里执行命令。即使模型执行了错误的命令，损失也被限制在沙箱里。

**钩子**（hooks）：在工具调用前后、会话开始和结束时运行你自己的代码，用来：
- 拦截危险命令（比如 `rm -rf`）；
- 每次改完代码自动跑格式化和测试；
- 记录审计日志。

钩子是**确定性的**：写在钩子里的规则一定执行，不依赖模型是否"记得"提示里的要求。

## 11.6 提示缓存与成本 **[事实 + 已证]**

**提示缓存**（prompt caching）：如果这次请求的开头和最近某次请求完全相同，服务端可以复用那一段已经算好的中间结果（注意力的 K、V，[6.4 节](ch06-self-attention.md#6.4)；服务端怎样存和查找这些结果，见 [17.5 节](ch17-inference-serving.md#17.5)）。命中缓存的部分，价格只有正常输入的一小部分，延迟也低得多。

**对 agent 的意义**：agent 循环里，每一轮的输入是"上一轮的输入 + 新的回复 + 新的结果"，天然只追加，所以大部分输入都能命中缓存。

**简单的成本模型**：设第 $t$ 轮输入长度为 $L_t$，其中前 $L_{t-1}$ 个 token 命中缓存，命中部分单价为 $\alpha$，新增部分单价为 $\beta$，则
$$\text{费用}=\sum_t\big[\alpha L_{t-1}+\beta(L_t-L_{t-1})\big].$$
不用缓存时是 $\sum_tL_t$。历史每轮增长 $\Delta$ 时，$L_t\approx t\Delta$，不用缓存的总费用约为 $\Delta T^2/2$，是轮数 $T$ 的**平方**；用了缓存，平方项的系数从 1 降到 $\alpha$。

**由此得到的工程规则** **[经验]**：
- 把稳定的内容放在前面：系统提示、工具定义，然后才是会变的对话历史；
- 不要在前缀里放每次都变的东西，比如当前时间戳；
- 工具列表保持确定的顺序（MCP 的最新规范也因此建议服务器按确定的顺序返回工具）；
- **压缩会破坏缓存**：历史被改写后，只剩固定前缀还能命中。所以压缩不能太频繁。

## 11.7 案例：一个编程 agent 的 harness **[事实]**

以编程助手为例（Claude Code、Codex CLI 等都属于这一类），把上面的部件对应起来：

| 部件 | 编程 agent 里的样子 |
|---|---|
| 工具 | 读文件、精确替换式编辑、搜索、执行 shell 命令、联网搜索 |
| 项目说明 | 仓库根目录的 `CLAUDE.md` 或 `AGENTS.md`：构建命令、代码规范、注意事项，每次启动自动加载 |
| 按需知识 | Skills（第 13 章） |
| 外部系统 | 通过 MCP 接入数据库、工单系统、浏览器等（第 12 章） |
| 进度跟踪 | 待办清单工具，让模型把计划写下来并逐项完成 |
| 上下文管理 | 截断大文件、自动压缩、子 agent 做探索 |
| 控制 | 权限模式（每次询问 / 自动接受编辑 / 只做计划）、沙箱、钩子 |
| 反馈 | 运行测试、类型检查、lint，结果作为工具结果返回 |

**反馈回路是关键** **[经验]**：让 agent 能自己验证结果（跑测试、看截图、对照规格），它就能在循环里自我修正。没有验证手段的任务，agent 只能"相信自己做对了"。

## 11.8 数值实验

代码：[`code/ch11_agent_harness.py`](code/ch11_agent_harness.py)，只用 Python 标准库，`python3 ch11_agent_harness.py` 直接运行。代码用一个规则写成的策略代替模型，重点放在 harness 上。

### 11.8.1 一个修 bug 的 agent

工作区里有 `calc.py`（`mean` 多加了 1）、`test_calc.py` 和一个临时文件 `notes.tmp`。任务："tests 挂了，修一下。"

| 轮 | 模型的动作 | 结果 |
|---|---|---|
| 1 | `list_files` | 三个文件 |
| 2 | 并行读 `calc.py`、`test_calc.py` | 看到 bug |
| 3 | "mean 多加了 1，去掉它"，`write_file calc.py` | 写入成功（在允许列表里） |
| 4 | `run_tests` | 1 passed |
| 5 | "顺手清理临时文件"，`delete_file notes.tmp` | **权限拒绝**，作为错误结果返回 |
| 6 | 总结：修好了，notes.tmp 没有删除权限，留给用户 | 循环结束 |

- 模型做了一件任务之外的事（删临时文件），被权限规则挡住了，`notes.tmp` 还在。
- 拒绝作为结果返回，模型在最终回答里如实说明，而不是卡住。
- 钩子记录了每次调用前后的审计日志，一共 12 条。

### 11.8.2 长任务的上下文与成本

模拟一个 40 轮的任务：系统提示 2000 token，工具定义 3000 token，每轮读一个 4000 token 的文件，模型每轮输出 150 token。缓存命中按 0.1 倍计价，写缓存按 1.25 倍计价。

| 策略 | 最大上下文 | 总输入 token | 相对费用 | 压缩次数 |
|---|---|---|---|---|
| 什么都不做，不用缓存 | 171,000 | 3,603,000 | 3,603,000 | 0 |
| 什么都不做，用缓存 | 171,000 | 3,603,000 | 556,950 | 0 |
| 截断到 1000 | 51,000 | 1,143,000 | 172,950 | 0 |
| 截断 + 压缩（预算 20k） | 19,950 | 574,650 | **130,778** | 3 |
| 截断 + 压缩，不用缓存 | 19,950 | 574,650 | 574,650 | 3 |

- 什么都不做时，上下文涨到 17 万 token，接近很多模型的窗口上限。
- 只打开缓存，费用就降到约 1/6.5：总输入不变，但大部分是缓存命中。
- 截断工具结果，最大上下文降到 1/3.4。
- 再加压缩，上下文始终在 2 万以内，费用最低。但对比最后两行：压缩之后缓存依然重要。

## 11.9 小结与疑问

**搞懂了什么**：
- 先用最简单的方案；步骤固定用 workflow，路径无法预知才用 agent。
- Agent 循环很简单，难的是 harness：工具、上下文管理、权限、反馈。
- 上下文管理靠截断、即时检索、压缩、笔记和子 agent。
- 安全控制放在 harness 里：权限分级、沙箱、钩子；拒绝也要作为结果返回。
- 提示缓存把只追加的 agent 循环的费用降低一个数量级；稳定内容放前面，压缩不要太频繁。

**疑问**：
- 压缩摘要应该保留什么？能否用评测（第 16 章）自动比较不同的压缩提示？
- 多 agent 协作什么时候比单 agent 好？上下文隔离的收益和信息丢失的代价怎样权衡？
