## 导读

前面十七章讲的东西，单独拿出来都能回答面试题；但面试官最常问的是"介绍一个你做过的项目"，然后围绕它追问几十个问题（[附录 C 的 C.14 节](appendix-c-interview-questions.md#C.14)）。这一章设计一个真正要做出来、上线、能被这样追问的项目：
- 做什么，为什么选它；
- 架构：前端、后端、模型网关、agent 循环、检索、记忆、可观测；
- 每个模块的关键设计决定，以及它对应哪些面试题；
- 怎么评测：评测集从哪来，看什么指标；
- 成本、延迟和安全；
- 分几步做，每一步交付什么。

本章最后做了第一个实验：拿附录 C 当标注，测几种检索方法在这本书上的效果。它不需要 API key，也不需要 GPU。

## 18.1 为什么做这个项目 **[经验]**

**项目**：一个围绕《大模型原理》这本书的学习助手，暂名"书伴"。它有三种模式：
- **问书**：用自然语言问书里的内容，回答附带出处，点一下就跳到书站对应的节；
- **面试**：从附录 C 里挑题问你，听你的回答，按"原理、数字、工程"三层追问，打分并给出参考答案和出处；
- **复习**：记住你哪些题答得不好，按间隔重复安排复习，显示附录 C 每一类的掌握情况。

**为什么选它，而不是做一个"企业知识库问答"** **[经验]**：

1. **评测集是现成的**。附录 C 的 366 道题里，117 道标了"✅ 能在第几节找到答案"，这就是"问题 → 正确文档"的标注；143 道标了"○ 书里没有"，正好用来测系统会不会胡编。大多数 RAG 项目做不好，是因为没有评测集；这个项目第一天就有（18.12 节）。
2. **语料有真实的难度**。中文为主、夹着英文术语、公式、代码和表格。中文分词、公式切块、中英混合检索，都是面试里会被追问的坑。
3. **你自己天天用**。这是它能被持续改进的前提，也让"用户反馈"成为真的数据，而不是编出来的。
4. **它覆盖了几乎所有类别的面试题**。下表是功能和附录 C 的对应：

| 功能 | 涉及的技术 | 对应附录 C |
|---|---|---|
| 流式聊天界面 | SSE、fetch 读流、中断、增量 Markdown、虚拟列表 | [C.10](appendix-c-interview-questions.md#C.10) 几乎全部 |
| 模型网关 | 超时、重试、回退、预算、路由、提示缓存 | [C.11.3](appendix-c-interview-questions.md#C.11.3)、[C.12.2](appendix-c-interview-questions.md#C.12.2) |
| 问书 | 切块、BM25 + embedding、RRF、重排、查询改写、引用 | [C.7](appendix-c-interview-questions.md#C.7) |
| 面试官 | 状态机 agent、工具调用、LLM 评委、评分标准 | [C.8](appendix-c-interview-questions.md#C.8)、[C.9.1](appendix-c-interview-questions.md#C.9.1) |
| 复习 | 长期记忆、冲突处理、间隔重复 | [C.8.3](appendix-c-interview-questions.md#C.8.3) |
| 评测与可观测 | 检索评测、拒答评测、评委校准、回归、trace | [C.9](appendix-c-interview-questions.md#C.9)、[C.13](appendix-c-interview-questions.md#C.13) |
| 上线 | 密钥管理、鉴权、限流、成本上限 | [C.9.3](appendix-c-interview-questions.md#C.9.3)、[C.11.3](appendix-c-interview-questions.md#C.11.3) |

**刻意不做的事**：不训练、不微调、不自建推理服务。模型用 API，项目的价值在模型之外的部分，也就是 harness（[11.3 节](ch11-agent-harness.md#11.3)）。后训练和推理服务各有自己的章节和实验。

## 18.2 功能与范围 **[经验]**

**第一版必须有**：
- 问书：回答带出处；书里没有时明确说没有；
- 面试：一次完整的出题、回答、追问、打分、总结；
- 流式输出、停止生成、刷新后对话还在；
- 每次请求的 token、延迟、费用都记下来；
- 离线评测脚本，一条命令跑完。

**第一版不做**：多用户、注册登录（用一个固定的访问令牌）、语音、移动端适配、联网搜索。

**非功能目标**（第一版先在本机测）：

| 指标 | 目标 | 依据 |
|---|---|---|
| 检索耗时 | p95 < 100 ms | 语料只有几百个块，不该成为瓶颈 |
| 首个 token（TTFT） | p50 < 2 s，p95 < 4 s | 用户感觉"有反应"；[17.11 节](ch17-inference-serving.md#17.11) |
| 检索 recall@5 | ≥ 0.90（附录 C 的 ✅ 题） | 基线是 0.88，见 18.12 节 |
| 引用有效率 | 100% | 引用必须指向本轮真的检索到的节，由代码检查，不靠模型自觉 |
| ○ 题的正确拒答率 | ≥ 0.8 | 书里没有的东西不能编成"书里说" |
| 每月费用 | 有硬上限 | API key 设消费上限，服务端再设每日 token 上限 |

## 18.3 架构 **[经验]**

```text
浏览器（React + TypeScript）
  ├─ 聊天界面：fetch 读流并解析 SSE；AbortController 停止
  ├─ 渲染：增量 Markdown + KaTeX，渲染前清洗
  ├─ 引用卡片：点开跳到书站的 #chN/N.k
  └─ 面试面板、复习面板（附录 C 覆盖图）
          │  HTTPS，自定义 SSE 事件
后端（Python，FastAPI + asyncio）
  ├─ /api/chat（流式）  /api/interview（流式）  /api/review  /api/traces
  ├─ agent 循环（自己写，复用第 11 章的 harness）
  │     工具：search_book · open_section · pick_question
  │           grade_answer · save_progress
  ├─ 检索：BM25（jieba）+ embedding + RRF，可选重排和查询改写
  ├─ 记忆：SQLite（题目掌握度、学习档案、会话摘要）
  ├─ 可观测：每次请求一条 trace，记 token、延迟、费用、检索结果
  └─ 模型网关：统一接口、超时、重试、回退、预算、路由
          │
模型 API（Claude：回答和追问用 Sonnet，查询改写和初评用 Haiku）
```

**几个关键选择和理由** **[经验]**：

1. **后端用 Python 的 FastAPI，而不是 Node**。你的强项是前端，Node 会更顺手；但 AI 工程岗的面试和生态都以 Python 为主（附录 C 里直接问过"FastAPI + asyncio 为什么适合调用大模型"），书里的代码也都是 Python。前后端用两种语言，正好两边都练到。
2. **agent 循环自己写，不用 LangChain**。核心循环只有一两百行（[11.2 节](ch11-agent-harness.md#11.2)），自己写的好处是每一行都讲得清楚；第 14 章的结论是框架在需要持久化、并行分支和大量集成时才划算（[14.5 节](ch14-langchain.md#14.5)），这里都不需要。面试被问"为什么不用框架"时，这本身就是一个好答案。
3. **存储只用 SQLite，向量直接用 numpy 暴力算**。全书切完只有约 280 个块（18.12 节）；就算 embedding 是 1024 维的 float32，也才 1 MB 出头，一次查询是一个 280×1024 的矩阵乘向量，远不到一毫秒。这时候上向量数据库和 HNSW 是过度设计。把检索写成一个接口，等语料大到几十万块再换 pgvector。"什么规模该换"本身就是面试题（[C.7.2](appendix-c-interview-questions.md#C.7.2)）。
4. **前后端之间用自己定义的 SSE 事件，不直接转发模型厂商的流**。前端只认自己的事件格式，换模型、加回退、插入工具进度，都不用改前端。这就是"模型网关"的意义。
5. **前端的流式核心写成和框架无关的 TypeScript 模块**。React 只负责渲染。以后换成 Angular 或者别的框架，核心不用动，也方便单独写测试。

## 18.4 前端：流式聊天界面 **[事实 + 经验]**

**为什么是 SSE** **[事实]**：模型本来就是一个 token 一个 token 生成的（[17.1 节](ch17-inference-serving.md#17.1)），流式只是把生成过程直接暴露给用户。只需要"服务器往浏览器推"这一个方向，所以用 SSE 就够了，不需要 WebSocket 的双向通道；SSE 走普通 HTTP，过代理和负载均衡也更省事。

**为什么不用 `EventSource`** **[事实]**：浏览器自带的 `EventSource` 只能发 GET 请求，不能带请求体，也不能自定义请求头。聊天要 POST 一整段对话，还要带访问令牌，所以改用 `fetch`，自己读 `response.body` 这个 `ReadableStream`，自己按 SSE 格式切事件。要处理的细节：
- 网络分包不按事件边界切：一个 chunk 里可能有半个事件，也可能有好几个，要有缓冲区，按空行切；
- 中文是多字节的：要用 `TextDecoder` 的流式模式（`stream: true`），否则一个汉字被切在两个 chunk 之间时会变成乱码；
- 事件可以有 `event:` 和 `data:` 两种字段，`data:` 可以多行。

**自定义事件** **[经验]**：

| 事件 | 内容 | 前端做什么 |
|---|---|---|
| `meta` | 本轮请求 id、用了哪个模型 | 显示在调试面板 |
| `token` | 一段新生成的文字 | 追加到当前消息 |
| `tool_start` / `tool_end` | 调用了哪个工具、参数摘要、耗时 | 显示"正在检索：KV cache" |
| `citation` | 本轮检索到的节和片段 | 渲染引用卡片 |
| `usage` | 输入、输出、缓存命中的 token 数，费用 | 显示在消息下方 |
| `error` | 错误类型、是否可重试 | 显示重试按钮 |
| `done` | 结束原因 | 解锁输入框 |

**停止生成** **[经验]**：
- 前端用 `AbortController` 取消 `fetch`；用户点停止、切换对话、组件卸载，都要取消，否则旧的流还在往已经不存在的组件里写；
- 后端要发现连接断了，并且**把上游的模型请求也取消掉**。只停前端不停后端，模型会继续生成、继续计费；
- 用户连点发送时，先取消上一个流再开新的，或者在上一个结束前禁用发送。

**增量渲染 Markdown** **[经验]**：
- 每来一个 token 就把整条消息重新解析一遍，消息长了会卡；只重新解析最后一个还没结束的块（段落、列表、代码块），前面已经结束的块缓存渲染结果；
- 代码块的围栏、公式的 `$` 还没闭合时，先按普通文本显示，闭合后再高亮或交给 KaTeX；
- 模型输出也是不可信的输入：渲染前用 DOMPurify 之类的库清洗 HTML，防 XSS。

**其他**：
- 自动滚动到底部，但用户往上翻时停止跟随，回到底部时恢复；
- 长对话用虚拟列表，只渲染可见的消息；
- 对话存在后端，刷新页面后从服务器恢复，不只靠 localStorage。

**部署时的坑** **[经验]**：本机好好的，放到 nginx 后面就变成一次性返回，通常是反向代理把响应缓冲了。要关掉代理的缓冲（或者返回 `X-Accel-Buffering: no`），并且确认没有中间层压缩整个响应。这是 [C.10 节](appendix-c-interview-questions.md#C.10) 里的原题。

## 18.5 后端：模型网关与 agent 循环 **[经验]**

**模型网关**：所有模型调用都经过它。它负责：
- **超时**：分两种，一是首个 token 多久没来，二是两个 token 之间多久没来。只设一个总超时，长回答会被误杀；
- **重试**：只重试可重试的错误（限流、过载、网络错误），指数退避加随机抖动，有上限；已经开始往前端输出 token 之后，不能悄悄重试，否则用户会看到两遍开头；
- **回退**：主模型持续失败时换备用模型，并在 trace 里记下来；
- **预算**：每个请求有 token 上限，每天有总上限，超了直接拒绝并告诉用户；
- **路由**：查询改写、初步打分这类简单任务给小模型，回答和追问给大模型（[16.8 节](ch16-evals-production.md#16.8)）；
- **提示缓存**：系统提示和工具定义放在最前面、保持不变，让它们命中缓存（[11.6 节](ch11-agent-harness.md#11.6)）。

**agent 循环**：问书模式其实不需要 agent，一个固定的"检索 → 生成"流程就够了（[11.1 节](ch11-agent-harness.md#11.1) 说过：能用 workflow 就别用 agent）。面试模式才需要：模型要自己决定追问还是换题、要不要查书核对。所以：
- 问书：workflow。检索由代码做，结果放进提示；
- 面试：agent。模型通过工具查书、取题、记录成绩；循环有最大步数和 token 预算，防止死循环（[11.2 节](ch11-agent-harness.md#11.2)）。

**工具** **[经验]**：按第 10 章的原则设计（[10.3 节](ch10-tool-calling.md#10.3)），粒度按"任务"而不是按"数据表"：

| 工具 | 输入 | 输出 |
|---|---|---|
| `search_book` | 查询、最多几条 | 节号、标题、片段 |
| `open_section` | 节号 | 这一节的正文（截断到一定长度） |
| `pick_question` | 类别、难度、是否优先复习 | 题目 id、题目、参考节 |
| `grade_answer` | 题目 id、用户回答 | 三个维度的分数和理由 |
| `save_progress` | 题目 id、分数、薄弱点 | 成功与否 |

只有 `save_progress` 会写数据，而且只写这个用户自己的学习记录；没有任何删除或执行代码的工具。权限的原则见 [11.5 节](ch11-agent-harness.md#11.5)。

## 18.6 检索 **[经验]**

**语料**：第 1–17 章和附录 A。附录 C 和本章都不进语料，因为它们包含评测题本身（18.12.1 节）。以后加上配套代码文件。

**切块**：按节切，节内按段落拼成不超过约 400 字的块；代码块和公式块先去掉，不进索引；每个块前面加上"第几章 · 第几节 · 节标题"（上下文化，[15.5 节](ch15-rag.md#15.5)）。

**第一版**：jieba 分词的 BM25 + 一个真正的 embedding 模型，用 RRF 融合。18.12 节的基线说明了三件事：
- 中文按词切比按字切好；
- 块前面加标题帮助很大；
- 剩下的失败大多是**用词不一致**：面试题说"防退化"，书里写的是"回归"；面试题说"串成的流水线"，书里写的是"可观测性"。这正是真 embedding 和查询改写该解决的问题。

**embedding 模型的选择**：候选是能在 CPU 上跑的多语言小模型（几百 MB 以内），或者 embedding API。语料只有几百个块，建索引一次几秒钟，所以本机就够，不需要 GPU。用 18.12 节的评测集比较，选分数高且延迟可接受的那个。

**之后的改进，每一项都要用评测集证明有用才保留**：
- 查询改写：用小模型把口语化的问题改写成书面的关键词，再检索；
- 重排：先取 20 个候选，再用更精确的模型排序；要量它增加了多少延迟（[C.7.2](appendix-c-interview-questions.md#C.7.2) 的"重排太慢能不能省掉"）；
- 多轮对话中的指代补全："那它的显存呢"要先补成"KV cache 的显存"再检索。

**生成时的约束**：
- 系统提示要求只根据检索到的片段回答，引用写成固定格式，比如 `[§17.3]`；
- 服务端检查每个引用是否真的出现在本轮检索结果里，不在的就删掉并记一条错误。引用有效率由代码保证，不靠模型；
- 检索的最高分低于阈值时，先告诉用户"书里可能没有讲到"，再决定要不要用模型自己的知识回答，并明确标出这部分不是出自本书。阈值用 ○ 题和 ✅ 题一起来定。

## 18.7 面试官模式 **[经验]**

**流程**是一个小状态机（和 LangGraph 的状态图是同一个思路，[14.4 节](ch14-langchain.md#14.4)）：

```text
选题 → 提问 → 等用户回答 → 评分 ─┬─ 有明显缺口且追问不到 3 次 → 追问 → 等用户回答 → 评分
                                  └─ 否则 → 给参考答案和出处 → 记录 → 选下一题或结束 → 总结
```

**选题**：按岗位筛类别；先选到期该复习的题，再选没做过的 ★ 题。

**评分标准**（每项 0–2 分）：
- **原理**：讲清楚为什么，而不只是是什么；
- **数字**：能给出关键公式、量级或估算；
- **工程**：能说出线上会遇到的问题和应对。

这三项来自附录 C 总结的追问方式（[C.1 节](appendix-c-interview-questions.md#C.1)）。

**评委要校准**（[16.5 节](ch16-evals-production.md#16.5)）：
- 模型评分时要拿到参考节的原文，而不是凭自己的知识打分；
- 先攒大约 30 个你自己打过分的回答，算模型评分和你的评分一致的比例；一致率不够就改评分提示，直到够为止；
- 评分时不告诉评委这个回答是谁写的，避免它偏向"看起来像模型写的"回答。

**追问的写法**：追问要针对回答里缺的那一层，而不是泛泛地"还有吗"。例如你答了"KV cache 缓存了 K 和 V"，缺的是数字，就追问"Llama-3-8B 一个 token 的 KV cache 有多大"。

## 18.8 记忆与复习 **[经验]**

**存什么**：

| 表 | 内容 | 什么时候写 |
|---|---|---|
| `question_progress` | 题目 id、作答次数、最近分数、下次复习时间 | 每次评分后 |
| `learner_profile` | 用户明确说过的事实，如目标岗位、已读到第几章 | 用户说了才写 |
| `session_summary` | 每次面试的摘要：答了哪些题、薄弱点 | 会话结束时 |

**间隔重复**：分数高，下次复习的间隔翻倍；分数低，间隔重置为一天。这是最简单的版本，够用。

**冲突与更新**：新事实覆盖旧事实时，旧的不删，标记为"已被替代"并记下时间。例如"目标岗位"从"算法岗"改成"AI 工程岗"，复习的选题范围跟着变，但历史还在。

**只写用户明确说过的话**：模型推断出来的东西（"他好像不擅长数学"）不写进档案。推断可能错，写进去就会一直影响以后的选题。

**为什么不用向量库存记忆**：记录是结构化的（题目、分数、时间），用 SQL 查"到期的题"最直接；只有会话摘要需要按语义找，数量少，暴力算就行。附录 C 里有一道原题就是问"为什么记忆用向量库而不是直接拼进提示"（[C.8.3](appendix-c-interview-questions.md#C.8.3)），这里的答案是"看数据是什么形状"。

## 18.9 评测 **[经验]**

**评测集**全部来自附录 C，不需要另外标注：

| 集合 | 来源 | 测什么 | 指标 |
|---|---|---|---|
| 检索集 | 117 道 ✅ 题和它们链接的节 | 检索能不能找到正确的节 | recall@k、MRR |
| 拒答集 | 143 道 ○ 题 | 书里没有时会不会编 | 正确拒答率；把"书里说"安在不存在的内容上的比例 |
| 生成集 | ✅ 题里抽一部分 | 回答是否忠实于引用的片段 | 忠实度（评委逐句核对）、引用有效率 |
| 评委校准集 | 你自己打过分的回答 | 评委和人是否一致 | 一致率 |

**标注的局限**：附录 C 里"哪道题对应哪一节"是我标的，不是独立的人工标注；有些题可以对应不止一节。所以：
- 先抽 30 道左右人工核对一遍，改掉明显错的；
- 失败的题要逐条看，有一部分会是标注的问题而不是检索的问题（18.12.3 节就有这样的例子）。

**回归**：每次改提示、换模型、改检索，都把整套评测跑一遍，和上一次逐题对比（配对比较，[16.4 节](ch16-evals-production.md#16.4)）。评测集只有一百来道题，95% 置信区间大约有 ±0.06 宽（18.12 节），所以 0.02 的差别不能算改进，要看逐题的变化。

**可观测**：每个请求一条 trace，记录：
- 检索：查询、改写后的查询、前 k 个结果和分数；
- 模型调用：模型、输入和输出 token、缓存命中的 token、首 token 延迟、总耗时、费用；
- 工具调用：名字、参数、结果大小、耗时、是否出错。

做一个简单的页面按天汇总。"用户说模型变笨了"时，先看 trace 有没有变化（[16.6 节](ch16-evals-production.md#16.6)）。

## 18.10 成本、延迟与安全 **[经验]**

**成本**：一次问书大约是
$$\text{费用} = n_{\text{缓存}}\,p_{\text{缓存读}} + n_{\text{输入}}\,p_{\text{输入}} + n_{\text{输出}}\,p_{\text{输出}},$$
- $n_{\text{缓存}}$：系统提示和工具定义，命中缓存的部分；
- $n_{\text{输入}}$：检索到的片段和对话历史；
- $n_{\text{输出}}$：回答。

单价以官方价格页为准 **[需核实]**；中文每个汉字大概对应多少 token 也因分词器而异，第一周就用响应里返回的 token 用量实测，而不是估计。面试模式每题有多轮，所以成本主要在对话历史上：历史超过一定长度就压缩成摘要（[11.4 节](ch11-agent-harness.md#11.4)），而且压缩会破坏缓存，要算清楚哪个划算。

**延迟**：
- 检索在本机内存里，应该是几毫秒；
- 首 token 延迟主要由模型决定，能做的是让提示前缀命中缓存、少放没用的片段；
- 查询改写和重排都会增加首 token 延迟，要实测再决定要不要上。

**安全**：
- **API key 只在后端**，放在环境变量里，不进代码、不进仓库、不发给浏览器。用一个单独的 key，设好消费上限；
- **后端要有访问令牌**。否则一旦部署到公网，任何人都能用你的 key；
- **限流**：按令牌限制每分钟请求数和每天的 token 数（令牌桶，[C.12.2](appendix-c-interview-questions.md#C.12.2) 的原题）；
- **提示注入**：语料是自己写的书，可信；不可信的只有用户输入和以后可能加的联网内容。工具都是只读的，唯一写入的工具只能写当前用户的学习记录，所以注入最多影响他自己的记录（[16.7 节](ch16-evals-production.md#16.7)）；
- **模型输出渲染前要清洗**，见 18.4 节。

## 18.11 里程碑 **[经验]**

按每周 10 小时左右估算。每个里程碑结束都写成书里的一章，带真实测出来的数字。

| 阶段 | 时间 | 交付 | 验收 |
|---|---|---|---|
| M0 骨架 | 第 1 周 | 仓库；FastAPI 和 React 骨架；模型网关（超时、重试、预算）；trace 表；跑通一次流式回答 | 能停止生成；trace 里有 token 和延迟 |
| M1 问书 | 第 2–3 周 | 检索 v1、引用与校验、完整的流式界面（中断、增量 Markdown、KaTeX、自动滚动） | recall@5 ≥ 0.90；引用有效率 100%；○ 题拒答率有基线 |
| M2 面试官 | 第 4–5 周 | 状态机、追问、评分标准、评委校准 | 评委和你的一致率达标 |
| M3 复习 | 第 6 周 | 掌握度、间隔重复、附录 C 覆盖图 | 连续用一周，复习题按时出现 |
| M4 优化 | 第 7–8 周 | 真 embedding、查询改写、重排的对比实验；缓存与路由；评测进 CI | 每项改动都有评测数字支持或否定 |
| M5 上线 | 之后 | 部署、鉴权、限流；可选：语音面试、在浏览器里运行书中代码 | 公网可用，费用在上限内 |

**做完以后，面试时的项目介绍**大概是这样的：
- 做了一个面向学习和面试的 RAG 加 agent 系统；
- 评测集来自 366 道面试题，其中 117 道有节级标注，143 道用来测拒答；
- 检索从基线的 recall@5 = 0.88 做到了多少，靠的是哪几个改动，各自贡献多少；
- 评委和人工的一致率是多少，怎么校准的；
- 首 token 延迟和每次的费用是多少，缓存和路由各省了多少；
- 踩过的坑：中文分包乱码、nginx 缓冲、引用造假、停止生成后后端还在计费。

每一条都有数字，每一个数字都能讲出怎么测的。这就是附录 C 里那些面经说的"能扛住追问"。

**开始前需要你准备的**：
- 一个单独的 API key，设好消费上限；
- 决定代码放在哪里。建议单独建一个公开仓库，方便以后放进简历；
- 前端默认用 React + TypeScript。如果你更想用 Angular，告诉我；流式核心和框架无关，只有渲染层不同。

## 18.12 数值实验

代码：[`ch18_eval_baseline.py`](code/ch18_eval_baseline.py)。只依赖 numpy；装了 jieba 会多跑两种按词切分的方法。不需要 API key，约 1 秒跑完。

### 18.12.1 评测集与语料

- 从附录 C 取出所有标了 ✅ 的题，它们链接的节就是正确答案。链接到小节的（比如 17.12.1）归到它所在的节（17.12）；只写了"第 15 章"的，整章都算对。
- 全书切成块，每块记住自己属于哪一节；检索返回块的排名，按第一次出现的顺序合并成节的排名；正确的节排在前 $k$ 名就算命中。

- 语料只用第 1–17 章和附录 A。本章引用了附录 C 的题和下面的结果，放进语料就是评测集污染：我第一次跑时没排除它，本章的节挤占了前几名，多数方法的 R@5 下降了 0.01–0.04。真实项目里同样要注意：评测题、标注说明、上一次的评测报告，都不能进被检索的语料。

```
评测集：117 道 ✅ 题（其中 ★ 67 道）；语料：278 个块，来自 143 个节
每题的正确节数：平均 1.46
```

### 18.12.2 六种检索方法

```
方法                                    R@1    R@3    R@5    MRR
BM25 · 字 bigram                       0.46   0.69   0.76   0.60
BM25 · 字 bigram · 加标题              0.58   0.79   0.83   0.70
BM25 · jieba                           0.50   0.75   0.85   0.65
BM25 · jieba · 加标题                  0.61   0.81   0.89   0.73
LSA（假 embedding）· 加标题            0.69   0.80   0.86   0.77
混合 RRF：BM25 + LSA · 加标题          0.68   0.83   0.88   0.77

最好的方法：混合 RRF：BM25 + LSA · 加标题；R@5 = 0.88，95% 区间 [0.82, 0.94]
只看 ★ 题：R@5 = 0.91（67 道）
```

- **按词切比按字切好**：不加标题时，R@5 从 0.76 升到 0.85。按相邻两个字切会产生大量跨词的无意义片段（比如"存的""么是"）。
- **块前加标题帮助最大**：两种切法的 R@1 都提高了约 0.1。很多块的正文没有提到它在讲什么（"它的显存……"），标题补上了这个信息，和第 15 章用玩具语料得到的结论一致（[15.8.3 节](ch15-rag.md#15.8.3)）。
- **没有一种方法全面领先**：LSA 的 R@1 最高（0.69），混合检索的 R@3 最高（0.83），jieba + 标题的 R@5 最高（0.89）。这三种方法之间的差别都在置信区间之内：117 道题只能分辨大约 0.06 以上的差别。脚本按 MRR 选"最好的方法"，混合检索和 LSA 并列，取了前者。
- LSA 在这里只是 embedding 的替身（第 15 章用过），真正的 embedding 模型要在 M1 和 M4 用同一个评测集来比。

### 18.12.3 失败的题

```
最好的方法在前 5 名里也没找到正确节的题（正确节 / 实际排第几）：
  [15.1 | 第 9 名] 有人想用微调让模型记住新出的政策条文，你怎么建议？
  [9.3 | 第 28 名] 角色提示有用吗？什么时候有用？
  [16.1、16.4 | 第 23 名] 怎么系统地评估和迭代一个提示？改提示或换模型后怎么防退化？
  [15.2 | 第 7 名] 画出一个 RAG 系统的完整流程。
  [15.2 | 第 23 名] 为什么要把长文档切块？不切会怎样？
  [11.1、11.2 | 第 11 名] agent 和普通聊天机器人、单次 LLM 调用的本质区别是什么？
  [11.2、11.3 | 第 6 名] agent 由哪些部分组成（模型、工具、记忆、规划）？
  [11.9 | 第 25 名] 让 LLM 当 agent 的核心有哪些局限？
  [10.1 | 第 6 名] function calling 的底层原理是什么？模型是怎么学会调用工具的？
  [10.3、11.4 | 第 6 名] 工具返回的结果很大，怎么交给模型？
  [16.4、16.6 | 第 10 名] 改了提示或换了模型，怎么发现退化？托管模型更新后行为变了，什么能发现？
  [16.6 | 第 128 名] 多个 LLM 串成的流水线里某一步出错，怎么定位？
  ……共 14 道
```

失败可以分成三类：

1. **用词不一致**（多数）：面试题说"政策条文""防退化""串成的流水线"，书里写的是"知识更新""回归""可观测性"。关键词检索对这种情况无能为力；真 embedding 和查询改写是对症的办法。
2. **概念题**："本质区别""由哪些部分组成"这类题，关键词在全书到处都有，答案却在某一节集中讲。重排可能有帮助。
3. **标注本身可以商量**：比如"角色提示有用吗"标的是 9.3 节，书里确实在那里提了一句，但只是一句话；检索排第一的节也许同样合理。这说明在用评测集比较方法之前，要先人工核对标注（18.9 节）。

## 18.13 小结与疑问

**搞懂了什么**：
- 项目选题的第一标准是"有没有评测集"。这本书的附录 C 自带 117 道检索标注和 143 道拒答测试题。
- 架构：自定义 SSE 事件把前端和模型厂商解耦；模型网关统一处理超时、重试、回退、预算和路由；问书用 workflow，面试用 agent；数据量小就用 SQLite 和暴力检索。
- 前端的难点在流的边界：分包、多字节字符、中断要传到后端、未闭合的 Markdown、渲染前清洗。
- 检索基线：jieba 分词 + 块前加标题 + 混合检索，recall@5 = 0.88，区间 [0.82, 0.94]；剩下的失败大多是用词不一致。

**疑问**：
- 真 embedding 能把 recall@5 提高多少？中文小模型和 embedding API 差多少？
- 查询改写值不值得它增加的首 token 延迟？
- 评委和人的一致率能做到多少？三项评分里，哪一项最难评准？
- 面试模式每题几轮对话，压缩历史省下的钱，够不够抵消缓存失效的损失？
